            <span id="prompt-cleaning" className='text-lightBeige/95 text-lg'>stage 1: prompt cleaning (gpt-4o)</span>
            <span className='text-lighterBeige font-inter font-extralight text-[1rem]'>

                so we run the user's prompt through gpt-4o with a heavily engineered system prompt:

                <div className='text-[0.65rem] md:text-[0.75rem] lg:text-xs'>
                    <pre className='line-numbers'>
                        <code className='language-python'>{`SYSTEM_PROMPT = """You create prompts for DALL-E that generate images
optimized for AI 3D model reconstruction.

YOUR #1 RULE: DO NOT change what the user asked for.
If they say "garden", generate a garden — NOT a "garden pavilion".

LANDMARK RECOGNITION - THIS IS CRITICAL:
When the user asks for a KNOWN LANDMARK (e.g., "CN Tower", "Eiffel Tower"):

            <span className='text-lightBeige/95 text-lg'>finding the right model</span>
            <span className='text-lighterBeige font-inter font-extralight text-[1rem]'>
                i spent a long time finding the optimal pipeline to model combination.

                my first attempt was running open source image to 3d models from <span className='text-lightBeige/95 font-normal'>hugging face</span> and deploying them on <span className='text-lightBeige/95 font-normal'>modal</span>. the idea was simple: host the model ourselves, avoid api costs, and control the pipeline end to end. 
                
                but in practice, the output quality was terrible. meshes were fried, textures were cooked, and inference times were way too long for an interactive tool. i tried a few different models on the hub and none of them produced anything close to usable for placing on an interactive map <span className='text-lightBeige/95 font-thin italic'>(panning, transforming, etc were all factors on top of the base model)</span>.

                after that i pivoted to fal.ai's hosted trellis model, and found that it was viable. it wasn't perfect, had to finetune many aspects of the pipeline, but at the end of the day, it does its job.
            </span>

            <span className='text-lightBeige/95 text-lg'>the multi image experiment</span>
            <span className='text-lighterBeige font-inter font-extralight text-[1rem]'>
                trellis supports a <span className='text-lightBeige/95 font-normal'>multi image mode</span>. you feed it multiple viewpoints of the same object, and it uses a stochastic algorithm to reconstruct better geometry than a single image can provide. in theory, more angles = more accurate mesh.

                so i tried generating <span className='text-lightBeige/95 font-normal'>four isometric views with dall-e</span>, front, back, left, and right, and feeding all four into trellis multi. the idea was to give the model complete coverage of the building.

                <span className='text-lightBeige/95 font-thin italic'>the generated model was ass.</span>

                the problem was <span className='text-lightBeige/95 font-normal'>shadows</span>. even though the system prompt explicitly says "no shadows", dall-e 3 subtly bakes directional shadows into every image, with soft gradients on surfaces, ambient occlusion at edges, and slight darkening on one side. these shadows are consistent <span className='text-lightBeige/95 font-thin italic'>within</span> a single image, but they're <span className='text-lightBeige/95 font-normal'>inconsistent across the four generated views</span>.

                trellis uses shading cues to infer surface depth and normal direction. when the lighting disagrees between images, one view has the left face bright and the right face dark, while another has the opposite. the reconstruction algorithm gets conflicting signals. it can't tell if a shadow is geometry (a recess or overhang) or just inconsistent lighting. the result was distorted meshes with phantom indentations and weird surface artifacts.

                <span className="route-background text-[0.9rem]">server/app/services/fal_service.py</span>
                <div className='text-[0.65rem] md:text-[0.75rem] lg:text-xs'>

            <span className='text-lighterBeige font-inter font-extralight text-[1rem]'>
                the search bar isn't just a geocoder. it's an <span className='text-lightBeige/95 font-normal'>ai powered intent parser</span> that understands natural language and maps it to actions.

                        autoPlay

                every search query goes through gpt-4o to classify intent into one of <span className='text-lightBeige/95 font-normal'>eight action types</span>:

                <span className="route-background text-[0.9rem]">server/app/services/openai_service.py</span>
                <div className='text-[0.65rem] md:text-[0.75rem] lg:text-xs'>
                    <pre className='line-numbers'>
                        <code className='language-python'>{`SEARCH_INTENT_PROMPT = """Parse user queries to understand their intent.
Users may have typos, misspellings, or use informal language.

1. **action**: One of:
   - "navigate": go to a specific location ("take me to Paris")
   - "find_building": find by characteristics ("tallest building here")
   - "set_weather": change weather ("make it rain")
   - "set_time": change time of day ("night mode")
   - "camera_control": adjust camera ("zoom in", "bird's eye")
   - "delete_building": remove a building ("delete the CN Tower")
   - "question": ask about a place ("how tall is the Burj Khalifa?")

CRITICAL RULES:
- use your world knowledge. "6th tallest building in the world"
  → navigate to "Goldin Finance 117, Tianjin, China"
- ALWAYS correct typos. "tke me to Prais" → "take me to Paris"
- For vague queries like "somewhere with good sunrises"
  → resolve to a REAL location: "Santorini, Greece"
"""
`}</code>
                    </pre>
                </div>

                what makes this powerful is how it handles <span className='text-lightBeige/95 font-normal'>typo correction, world knowledge resolution, and vague queries</span> simultaneously. "tke me to the eifel twoer" correctly resolves to "eiffel tower, paris". "bring me somewhere cold asf" could resolve to "tromsø, norway".
            </span>

            <span className='text-lightBeige/95 text-lg'>building search</span>
            <span className='text-lighterBeige font-inter font-extralight text-[1rem]'>
                for <span className="route-background text-[0.9rem]">find_building</span> queries like "tallest building here", we fetch real building data from <a href="https://wiki.openstreetmap.org/wiki/Overpass_API" target="_blank" className="a">openstreetmap's overpass api</a> with failover across multiple endpoints. buildings are ranked by the query's attribute: height, footprint area, or an "underdeveloped" heuristic that finds buildings with <span className='text-lightBeige/95 font-normal'>large footprints relative to their height</span> (high area to height ratio = a lot of land "wasted" on a short building).

                the <span className="route-background text-[0.9rem]">delete_building</span> action is fun. it geocodes the building, then generates a deletion polygon around it scaled to the building type. towers get small, precise polygons; stadiums and arenas get larger ones since they're wide.
            </span>

            <span className='text-lightBeige/95 text-lg'>geocoding</span>
            <span className='text-lighterBeige font-inter font-extralight text-[1rem]'>
                building selection uses <a href="https://nominatim.openstreetmap.org/" target="_blank" className="a">nominatim</a> for reverse geocoding. we wrote a display name shortener that strips long addresses into readable labels:

                <span className="route-background text-[0.9rem]">server/app/services/geocoding_service.py</span>
                <div className='text-[0.65rem] md:text-[0.75rem] lg:text-xs'>
                    <pre className='line-numbers'>
                        <code className='language-python'>{`def shorten_display_name(full_name: str, address_details=None):
    # Full: "CN Tower, 301 Front Street West, Toronto, Ontario, Canada"
    # Short: "CN Tower, Toronto, Canada"

    if address_details:
        parts = []
        for key in ["tourism", "building", "amenity"]:
            if key in address_details:
                parts.append(address_details[key])
                break
        # ... city, country
        return ", ".join(parts)
`}</code>
                    </pre>
                </div>

                this prevents addresses like "cn tower, 301 front street west, entertainment district, toronto, golden horseshoe, ontario, m5v 3t6, canada" from cluttering the ui. it strips down to "cn tower, toronto, canada".
            </span>
        </div>

            <span className='text-lightBeige/95 text-xl'>performance</span>
            <span className='text-lighterBeige font-inter font-extralight text-[1rem]'>
                rendering 3d models on a mapbox map in the browser required careful optimization. heavy components like the toolbar, search bar, generator panel, and transform gizmo are wrapped with <span className="route-background text-[0.9rem]">React.memo()</span> to prevent rerenders when the map moves. modals and the tutorial are loaded with <span className="route-background text-[0.9rem]">next/dynamic</span> and <span className="route-background text-[0.9rem]">ssr: false</span> to keep the initial bundle small.

                one subtle issue: mapbox event handlers are registered once during initialization. without refs, they capture stale state from the initial render. so every piece of state that mapbox callbacks need is synced to a ref:

                <div className='text-[0.65rem] md:text-[0.75rem] lg:text-xs'>
                    <pre className='line-numbers'>
                        <code className='language-ts'>{`const activeToolRef = useRef(activeTool);
useEffect(() => {
    activeToolRef.current = activeTool;
}, [activeTool]);
// ... same for deletedFeatures, insertedModels, isPlacingModel, etc.
`}</code>
                    </pre>
                </div>

                this pattern repeats for about a dozen state variables. it's not elegant, but it's necessary for mapbox's callback model.
            </span>
        </div>
